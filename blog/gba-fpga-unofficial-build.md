# Building a GBA-Shaped FPGA Handheld Without Pretending a 20K FPGA Is a 60K FPGA

The most dangerous part of a retro FPGA project is not soldering the cartridge connector backwards. It is confusing three very different statements:

- a board has “20K” in its name;
- an FPGA core reports roughly 26,000 logic elements;
- a complete handheld will fit once video, memory, storage, controls, and audio are added.

Those statements are not interchangeable.

I already had the start of a useful ecosystem: **GBA Studio**, an experimental visual toolchain that produces native Game Boy Advance ROMs, and **GBA Engine**, the C runtime that those projects compile against. I also had a Tang Nano 20K, a GBA-style button PCB, a 4.3-inch 480x272 IPS panel, and the entirely reasonable desire to turn the pile into something resembling a modern FPGA handheld.

The resulting project is called **GBA-FPGA**, but the first useful result is a constraint, not a bitstream: the Nano 20K is a good Game Boy board and a poor FPGBA board.

## The resource mismatch

Sipeed's Tang Nano 20K uses the Gowin GW2AR-LV18 and provides 20,736 LUT4s, 828 Kbit of block SRAM, and 64 Mbit of external SDR SDRAM. Those are strong resources for a board barely larger than a stick of gum. They are enough for projects such as GBTang, which recreates the original Game Boy and adds an SD-card menu, HDMI output, sound, and controller support.

The available FPGBA core is a different scale. Its upstream documentation reports about 26,000 logic elements and 2 Mbit of RAM for the GBA implementation alone, before a framebuffer and platform peripherals. The core also expects slower WRAM, Game Pak ROM, and saves to live in external SDRAM.

Even before converting “logic elements” between vendor architectures, the arithmetic is unfriendly. The core's stated logic use is larger than the Nano 20K's entire LUT budget. Its stated internal-memory use is more than twice the Nano's block RAM.

Could a determined engineer redesign the memory system, spill more state into SDRAM, simplify optional features, and spend months squeezing the result? Possibly. But that is not a port. It is a new architecture project whose hardest problem becomes deterministic memory latency.

So the repo makes the decision explicit:

- **Tang Nano 20K:** use GBTang for GB/GBC and develop the handheld peripherals.
- **Tang Mega or Console 60K:** use GBATang for a working GBA implementation.
- **FPGBA on Tang 60K:** maintain a separate research port with honest completion criteria.

That separation prevents the familiar open-hardware failure mode where a repository contains a top-level file, a constraint template, and a README that somehow turns those into a “working build.”

## The practical GBA route already exists

GBATang targets the Tang Mega 60K, Tang Mega 138K family, and Tang Console 60K. It provides 720p HDMI, controller input, SD loading, an open BIOS path, and support for ROM images up to 32 MB. Its maintainers describe it as a port that evolved into a substantial rewrite of the MiSTer GBA core, including a different CPU and memory system.

That makes it the correct execution target for the ROMs generated by GBA Studio.

The boundary is deliberately boring:

```text
GBA Studio project
        |
        v
GBA Engine + generated assets
        |
        v
devkitARM produces game.gba
        |
        v
GBATang loads game.gba from SD
```

GBA Studio is not an FPGA compiler. GBA Engine is not a soft CPU. They create software for GBA-compatible hardware. The FPGA core supplies that hardware.

This distinction is useful because it gives the project a clean test matrix. A homebrew build can run in mGBA, on GBATang, and on a real GBA or flash cartridge. A failure across all three probably belongs in the game or runtime. A failure isolated to the FPGA is evidence for the core or platform integration.

## What the Nano 20K is still good for

Rejecting FPGBA on the Nano 20K does not make the board redundant. It makes the development sequence more disciplined.

GBTang can validate the complete handheld experience at the GB/GBC level: SD loading, buttons, audio, power behaviour, and enclosure. The same board can also bring up the raw LCD and cartridge interface before the GBA core moves to 60K hardware.

The 480x272 panel deserves particular care. A product listing that says “480x272 IPS” does not reveal whether the panel is RGB565, RGB666, RGB888, SPI, or 8080-style parallel. It does not reveal the FPC pinout, I/O voltage, porch timings, sync polarity, or backlight current. Until the exact panel part number is known, a constraint file is guesswork with a non-zero chance of destroying the display.

Once the interface is confirmed, the geometry is manageable. A GBA frame is 240x160, or 3:2. The largest 3:2 image that fits inside 480x272 is 408x272, leaving 36-pixel borders on each side. A nearest-neighbour coordinate mapper can preserve every source pixel without stretching the image to the panel's wider aspect ratio.

The repository includes that mapper and a separate LCD timing generator so the panel can show color bars before any game core is connected.

## A cartridge slot is a bus, not a socket

The cheap button PCB is passive. The cartridge connector is not.

A GBA cartridge presents a 16-bit multiplexed lower-address/data bus, eight dedicated upper-address lines, and control signals. During a read, the host first drives the address, asserts chip select so the cartridge latches it, releases the multiplexed bus, and then asserts read while the cartridge drives data back.

Bus ownership is the critical detail. If the FPGA and cartridge drive `AD[15:0]` at the same time, the best outcome is a failed read. The worse outcome is damaged hardware.

The ROM reader in GBA-FPGA therefore uses an intentionally conservative finite-state machine:

1. drive the address;
2. assert `/CS`;
3. release the bus;
4. wait for turnaround;
5. assert `/RD`;
6. sample one halfword;
7. recover;
8. repeat.

It holds `/WR` inactive and implements no save protocol. That is slower than a burst reader, but it is testable and safe enough for initial hardware validation.

For the final handheld, a companion RP2350 is the better architecture. A raw RGB LCD can consume more than twenty FPGA pins. A direct GBA cartridge reader consumes roughly another twenty-six. A dedicated 3.3 V MCU can own the cartridge connector, dump ROM and saves to SD or USB, and transfer a file to the FPGA loader. It also isolates save writes from the real-time core, where power failure and protocol mistakes are much harder to contain.

## The lesson from a 60 Hz e-ink Game Boy

Wenting Zhang's PaperBoy S3 project looks unrelated at first: it runs a Game Boy emulator on an ESP32-S3 and displays it on e-ink. The useful lesson is architectural rather than aesthetic.

Conventional e-ink refreshes are slow because a pixel needs sustained drive time. PaperBoy S3 does not make the particles move instantly. Instead, it removes the global frame lock and tracks each pixel's drive state across multiple 60 Hz frames. New image data can arrive every frame while the state buffer ensures each pixel receives the required sequence.

That would be expensive at the panel's full 960x540 resolution. It becomes practical because the Game Boy image is only 160x144. The workload geometry turns an apparently unsuitable display into a playable one.

The project applies the same reasoning elsewhere. It tests multiple emulator cores and uses the most efficient one rather than rewriting the emulator for novelty. It puts the display and sound work on the second ESP32 core. It accepts that a buzzer will not reproduce the Game Boy audio chain accurately, then creates a recognisable single-buzzer approximation. It exposes save as an explicit user action because the power switch can cut power before an automatic flush completes.

That is the standard I want for GBA-FPGA: choose the hard constraint, measure it, and publish the compromise. Do not hide frame skipping, incomplete controller support, imperfect audio, missing save writeback, or an FPGA that simply does not have enough memory.

## What the unofficial FPGBA build actually contains

The “FPGBA Tang 60K build” in the repository is an integration scaffold with a strict refusal to generate a misleading release artifact.

It defines:

- the platform-facing reset and clock contract;
- active-low GBA joypad mapping;
- ROM and save-memory interfaces;
- video and audio stream boundaries;
- a Tang constraint template;
- the upstream VHDL compilation order;
- the milestones required before the port can be called working.

The missing work is substantial: Gowin RAM mapping, DDR3 arbitration, clock generation, a loader, framebuffer integration, audio output, constraints, timing closure, and hardware validation.

A real completion report will need the exact FPGA part, Gowin tool version, resource utilisation, timing report, legal homebrew test image, and known incompatibilities. Until those exist, the practical build remains GBATang on 60K hardware.

## A handheld can be built in layers

The project now has a realistic sequence:

1. Use the Nano 20K and GBTang to validate controls, SD, audio, and the enclosure.
2. Identify and bring up the 480x272 panel independently.
3. Validate ROM-only cartridge reads with current limiting and a logic analyser.
4. Build GBA Studio homebrew and test it in an emulator.
5. Move the hardware design to Tang 60K and run the same ROM with GBATang.
6. Add the companion cartridge reader and save backup.
7. Continue the FPGBA port as a separate research track.

The end result can still look like a sleek GBA. It can still load from SD, read physical cartridges, and run my own GBA Studio projects. The difference is that every layer has a test boundary, and none of the documentation asks a 20K FPGA to become a 60K FPGA through optimism.

## Repository

The GBA-FPGA repository includes the RTL modules, self-checking testbenches, platform scaffold, Windows and Linux scripts, cartridge documentation, panel-integration notes, and the complete article source. It intentionally excludes BIOS images and commercial ROMs.

The first release is not a finished console. It is the point where the project becomes buildable without becoming fictional.
